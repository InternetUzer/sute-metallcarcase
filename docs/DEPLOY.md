# Размещение на сервере владельца

Вариант поставки: VPS с Docker Engine и Compose, собственный домен, постоянный диск. Убедитесь, что сервер подходит под ваши требования к размещению данных. Зависимости доступны в исходниках; аккаунт Megagroup не нужен.

## Первый запуск

1. Скопируйте репозиторий на VPS. Создайте `.env` из `.env.example`.
2. Сгенерируйте SECRET_KEY: `python3 -c "import secrets; print(secrets.token_hex(32))"`. Храните значение только в `.env`, не в переписке и Git.
3. Укажите `SITE_HOST`, `SITE_URL` и `TRUSTED_HOSTS` для временного домена. Например: `test.example.ru`, `https://test.example.ru`, `test.example.ru`. Создайте A-запись временного домена на IP сервера. `SITE_INDEXABLE=0`.
4. Откройте 80/443 для Caddy. Порт 8000 не публикуйте в интернет. `TRUST_PROXY=1` корректен только за одним доверенным Caddy, как в комплектном compose. При другом окружении настройте доверие прокси отдельно.
5. `docker compose up -d --build`.
6. `docker compose exec web flask --app 'app:create_app' create-admin`. Пароль — не менее 12 символов; выберите уникальный длинный пароль.
7. Проверьте `docker compose logs --tail=100 web caddy`, HTTPS, заявки, вход и документы двух разных клиентов.

## Почта

Заполните SMTP_HOST, SMTP_PORT, SMTP_USER, SMTP_PASSWORD, SMTP_FROM, NOTIFY_EMAIL. Поддерживаются STARTTLS на 587 и TLS на 465. Используйте пароль приложения почтового провайдера, если он требуется. После изменения окружения выполните `docker compose up -d --force-recreate web`.

Без SMTP заявка сохраняется в панели владельца, но письма не отправляются. Создание приглашения показывает владельцу одноразовую ссылку, которую он передаёт клиенту самостоятельно. Восстановление по email работает после настройки SMTP. Отправьте реальную контрольную заявку и проверьте восстановление доступа перед запуском.

## Обновление кода

Сохраните резервную копию, получите обновления из GitHub и выполните `docker compose up -d --build`. Именованный том `site_data` сохраняется. **Не выполняйте `docker compose down -v`: команда удаляет постоянные данные.** Текущая версия создаёт схему при первом старте; изменения схемы в будущих версиях требуют отдельной миграции.

## Резервная копия

Команда создаёт согласованный снимок SQLite и копию файлов. Во время копирования не загружайте новые документы. Для надёжной копии временно остановите web и выполните CLI в отдельном контейнере:

```bash
docker compose stop web
docker compose run --rm web flask --app 'app:create_app' backup /data/backup.tar.gz
docker compose cp web:/data/backup.tar.gz ./backup.tar.gz
docker compose start web
```

Если копирование из остановленного контейнера не поддерживается вашей версией Compose, сначала запустите web и повторите `docker compose cp`. Имя файла должно быть новым: CLI не перезаписывает существующий архив. Перенесите архив в закрытое резервное хранилище. Не добавляйте архивы в Git и не оставляйте только на том же VPS.

Восстановление: остановите web, сохраните текущий том отдельно, распакуйте доверенный архив в `site_data` (в корне должны быть `site.sqlite3` и `files/`), удалите старые `site.sqlite3-wal`/`site.sqlite3-shm` от прежней базы, восстановите владельца файлов UID 10001 и запустите web. Сначала отрепетируйте восстановление на отдельном тестовом томе.

## Ограничения первой версии

SQLite и локальные вложения рассчитаны на один сервер. Для нескольких экземпляров потребуется общая база и хранилище. Есть ограничения на частоту запросов и размеры файлов, но нет общего дискового лимита, антивируса вложений, двухфакторного входа и журнала административных действий. Следите за свободным диском, храните резервные копии, обновляйте зависимости. Загрузка файлов: максимум три, до 10 МБ каждый, до 25 МБ вся отправка. Файлы выдаются только скачиванием с проверкой доступа.

Визуальная проверка в браузере на доступном HTTPS-адресе и реальная SMTP-проверка входят в запуск: в среде разработки доступ браузера к локальному серверу был заблокирован. Docker-конфигурация подготовлена, но запуск контейнеров здесь не проверялся.
